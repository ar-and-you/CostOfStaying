## 1. قواعد التنفيذ

1. `main` هو مصدر الحقيقة؛ لا تُستبدل ملفات الفرع بأرشيفات قديمة.
2. لا استيراد جماعي لـADR أو وثائق ZIP. كل مصدر يراجع ببصمته وتاريخه وتعارضاته.
3. لا تغيير في Domain/Core أو قواعد اللعب أو التوازن قبل قرار مالك صريح وADR عند اللزوم.
4. افصل بين `PROPOSED`, `PROPOSED FOR PLAYTEST`, `APPROVED`, `IMPLEMENTED`, `VERIFIED`, و`TBD`.
5. كل تحقق يسجل SHA والبيئة والأمر/Workflow والنتيجة والنطاق؛ نجاح CI لا يثبت Unity أو Android أو شبكة أو اختباراً بشرياً.
6. لا force-push ولا إعادة كتابة للتاريخ. اتبع سياسة الدفع الحالية إلى `main` إلى أن يقرر المالك خلاف ذلك.
7. لا تنشئ وثيقة أو workflow مكرراً إذا كانت وثيقة قائمة تغطي الغرض.

## 2. خط الأساس المتحقق

- HEAD وقت المراجعة: `ad22b9ddb21ca48f9e30aa7f3560cf3e56f632c4`.
- ستة check-runs على هذا SHA اكتملت بنجاح: Domain/Python، Core، Documentation Governance، وثلاث وظائف CodeQL (C#, Python, Actions). هذا يثبت تشغيلات SHA هذا فقط.
- `docs/adr/` يحتوي الفهرس والقالب ولا يحتوي ADR مقبولاً.

- توجد بالفعل خطط اختبار اللعب البشري، واستراتيجية الاختبارات، واختبارات الأمن، وميزانية/بروتوكول الأداء، وتوافق الأجهزة، وخطة Unity mobile CI؛ يجب تحديث الموجود لا إنشاء نسخ موازية.

## 3. مسارات العمل

### A — مصالحة ADR والحوكمة
- جرد جميع سجلات ADR في الأرشيفات والمستودع، مع المصدر والبصمة والتاريخ والعنوان والحالة.
- إنشاء مصفوفة تعارض، وبالأخص نسخ ADR-005 المتنافسة، ومراجعة مقترح ADR-028 لسياسة الفروع.
- مقارنة كل قرار مرشح بالكود والوثائق الحية؛ لا يستدل من تعليقات الكود أو رقم ADR وحده على الاعتماد.
- إعداد حزمة قرارات للمالك، ثم استيراد السجلات المتسقة فقط بعد الموافقة.

### B — حدود Domain/Core
- وصف المسؤوليات الحالية والاعتماديات وواجهات API والاختبارات.
- إعداد بدائل مع تحليل التوافق والتراجع قبل أي نقل أو دمج.
- حسم تمثيل Vitality (الوحدة والنطاق والدقة والتحويل)، ودلالات حالات اللاعب، ومالك الحقيقة لحالة اللعب.
- لا يبدأ ترحيل غير قابل للعكس قبل D1 وD2 وموافقة المالك.

### C — قرارات قواعد اللعب ودورة الحياة
- حسم LastSurvivor مقابل TimeLimit، ونهاية المباراة، والموت/Spirit، والانقطاع وإعادة الاتصال، والتصويت.
- مراجعة اقتصاد Spirit وCollapse وSuffering Transfer وBetrayal دون اعتماد أرقام من تلقاء المنفذ.
- تحديد منظور العرض/الكاميرا كقرار تجربة مستخدم منفصل عن قواعد Domain.
- تحديد أن قياس المسافة والتحقق المكاني سلطة خادم عند وجود خادم فعلي؛ تمرير قيمة distance إلى Domain ليس إثباتاً لقياس موثوق.

### D — الجودة والأدوات
- توسيع الاختبارات الحتمية واختبارات replay/property-based حيث تكون مفيدة.
- فحص `tools/audit.py` واختبارات إعداد GitHub وأدوات المحاكاة قبل استيرادها.
- توثيق سياسات bots وحدودها، وإظهار فواصل الثقة/تكرار التجارب عند تحليل sweeps.
- لا تسمى اختبارات Python الحالية تكافؤاً مباشراً مع C#.

### E — CI/CD والأمن
- إعادة التحقق من branch protection وrulesets بصلاحية مناسبة، كل endpoint على حدة.
- مراجعة CodeQL وDependabot alerts عند توفر الصلاحيات؛ 403 ليس دليلاً على خلو التنبيهات.
- تقييم Dependabot security updates وسياسة PRs قبل التفعيل.
- معالجة تحذيرات XML docs، وتثبيت Actions على SHAs، وإضافة فحوص workflow/supply-chain بعد مراجعة فائدتها.
- لا تضف Unity/Android workflows قبل وجود مشروع وبناء فعليين وأسرار محفوظة خارج Git.

### F — Unity vertical slice
- تنفيذ spike استكشافي بعد تجهيز قرارات النطاق، لا اختيار إصدار/حزمة نهائية قبل إثبات prototype.
- اختبار استهلاك مكتبات Domain/Core، توافق IL2CPP وlink.xml، وساعة monotonic adapter.
- بناء offline slice صغير: لاعب بشري واحد وثلاثة bots، ثم Android build وقياس على جهاز فعلي.
- Android هو الهدف الأول الموثق؛ لا يفترض اعتماد iOS.

### G — الخادم والشبكة
- تقييم FishNet وUnity NGO وtransport مخصص على معايير authority والتكلفة والتشغيل والاختبار.
- إبقاء العميل intent-only، والتحقق من الحركة/المسافة/الضرر على الخادم.
- تصميم الجلسات وإعادة الاتصال ومنع replay وrate limiting وtelemetry.
- اختبار RTT/loss/jitter/reordering وreconnect قبل قرار الاستضافة.
- لا يوصف Core الحالي بأنه خادم أو تكامل شبكة إنتاجي.

### H — اختبار اللعب والتوازن
- تطبيق `PLAYTEST_PLAN.md` الموجود، مع موافقة ومشاركة طوعية وبيانات مستعارة واحتفاظ/حذف محددين.
- الحصول على 10 جلسات بشرية صالحة على الأقل قبل استخلاص توصيات توازن؛ العدد شرط لازم وليس كافياً.
- فصل نتائج bots والمحاكاة عن الأدلة البشرية.
- لا تعتمد قواعد أو قيم إلا بقرار مالك مكتوب بعد مراجعة النتائج.

## 5. ترتيب التنفيذ المقترح

1. **المرحلة 0 — تأسيس الأدلة:** إكمال مصالحة الأرشيف، تصحيح الفهارس، وتحديث سجل CI والإعدادات ببيانات SHA الحالية.
2. **المرحلة 1 — قرارات الحوكمة:** حزمة ADR والتعارضات ثم موافقات D1 وD3.
3. **المرحلة 2 — قرارات المنتج والعقد:** D-R1..D-R7 ثم D2؛ التحليل والتحضير يمكن أن يسيرا بالتوازي، أما الترحيل فينتظر.
4. **المرحلة 3 — جودة وأمن:** تحسين الاختبارات والسياسات بناء على العقد المعتمد، وإغلاق فجوات صلاحيات GitHub.
5. **المرحلة 4 — spikes تقنية:** Unity/Android وnetwork transport تجريبياً، ثم D5a/D5b.
6. **المرحلة 5 — خادم وتكامل:** تطوير authority/reconnect/security ثم قرار D6 قبل النشر.
7. **المرحلة 6 — لعب بشري:** D7، ثم جلسات منظمة، ثم D8.
8. **المرحلة 7 — خروج Pre-production:** D9 بعد اكتمال معايير المنتج والهندسة والتشغيل.
