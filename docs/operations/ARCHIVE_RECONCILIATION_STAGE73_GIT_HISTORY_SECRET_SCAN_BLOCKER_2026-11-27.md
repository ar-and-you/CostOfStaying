## 2. الأدلة الحالية ذات الصلة

- `docs/security/SECRETS_MANAGEMENT.md` يذكر أن آخر حالة معروفة لـSecret scanning وPush protection كانت active في قراءة 2026-11-24، لكن لا توجد قراءة أحدث مؤكدة في هذه المرحلة.
- الوثيقة نفسها تسجل أن فحص الأنماط غير التابعة لمزود وفحوص صلاحية الأسرار كانت معطلة في آخر قراءة متاحة.
- لا يوجد تقرير حديث في المستودع يثبت مسحاً كاملاً لتاريخ Git بواسطة أداة متخصصة.
- صلاحيات GitHub المتاحة في بيانات المستودع لا تشمل `admin`; لذلك لا يمكن من هذا الاتصال تغيير إعدادات Secret scanning أو قراءة جميع التنبيهات الإدارية.
- وجود قواعد `.gitignore` أو Secret scanning على GitHub لا يمحو أسراراً تاريخية ولا يثبت أن كل كائنات Git فُحصت.

## 3. ما لم يُدّعَ

- لم يُعلن أن المستودع خالٍ من الأسرار.
- لم يُعلن أن تاريخ Git خضع لمسح كامل.
- لم تُحذف ملفات أو التزامات أو refs.
- لم يُجرَ rewrite للتاريخ ولم يُستخدم force-push.
- لم تُعرض أي قيمة سرية أو تُنسخ إلى التقرير.

## 4. مسار الإغلاق المطلوب

يلزم تشغيل موثوق لديه وصول إلى clone كامل للمستودع، ثم:

1. الحصول على mirror clone مع جميع refs المطلوبة، وتسجيل وقت الفحص وHEAD والrefs التي جرى جلبها.
2. تثبيت إصدار Gitleaks معروف وتسجيل رقم الإصدار وبصمة الأداة/بيئتها.
3. تشغيل فحص تاريخي شامل، مثلاً `gitleaks git --redact --report-format json --report-path gitleaks-history.json .` بعد التحقق من خيارات الإصدار المثبت.
4. حفظ التقرير في مكان خاص وآمن؛ لا ترفع التقرير الخام إذا كان قد يتضمن snippets أو قيماً حساسة.
5. مراجعة النتائج يدوياً وتصنيف false positives، مع الاحتفاظ بالمعرّفات والبصمات والمواضع دون نسخ قيمة السر.
6. إذا ثبت تسريب سر: إبطاله/تدويره أولاً لدى المزود، ثم تحديد الالتزامات المتأثرة وخطة المعالجة. لا تُعد كتابة Git history دون موافقة صريحة وخطة تنسيق مع جميع المستنسخين.
7. إعادة الفحص بعد المعالجة، وتوثيق SHA/refs والأداة والنتيجة النهائية.
