## 4. ما لا ينبغي فعله

- لا نسخ جماعي لملفات ADR الأرشيفية إلى `docs/adr/`.
- لا إعادة استخدام رقم ADR-005 أو ملء ADR-024 من دون قرار موثق عن المصدر والتسلسل.
- لا وصف أي سجل أرشيفي بأنه ACCEPTED على `main`، حتى لو احتوى نسخة المصدر على كلمة APPROVED.
- لا تحويل تنفيذ Core أو نجاح NUnit إلى موافقة معمارية أو سياسة gameplay.
- لا دمج Domain/Core، ولا تغيير دورة حياة اللاعب أو قيم اللعب أو سياسة الفروع بسبب هذه المصالحة.
- لا حذف النسخ المتنافسة؛ تحفظ provenance والبصمات والنسخ التاريخية.

## 5. شروط إغلاق D1

1. يراجع المالك قائمة المرشحات والتعارضات أعلاه ويحدد أي الموضوعات تستحق ADR مستقلاً.
2. يحدد المالك المرجع التاريخي الذي يجيز استخدامه، إن وجد، وكيفية التعامل مع تعارض ADR-005 وفجوة ADR-024.
3. يحدد ترقيم السجلات الجديدة أو يوافق على ترقيم جديد بعد توثيق عدم الالتباس.
4. تُكتب ADR واحدة لكل قرار معماري طويل الأثر، بحالة `PROPOSED` أولاً، مع سياق وبدائل وتبعات وأمن/خصوصية وتنفيذ واختبارات وترحيل/تراجع.
5. لا تصبح الحالة `ACCEPTED` إلا بقرار مالك صريح ومكتوب، ثم تُحدّث `docs/adr/README.md` و`docs/README.md` و`ROADMAP.md` وسجل القرارات المفتوحة وفقاً لذلك.
6. لا تُستخدم ADR لتجاوز قرارات المنتج أو متطلبات playtest أو صلاحيات GitHub.
